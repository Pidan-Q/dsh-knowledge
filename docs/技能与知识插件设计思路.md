# DeepSeek Harness 技能管理与知识学习插件设计思路

> 目标平台：DeepSeek Harness（DSH），基于 Cordis 元框架的开源 Agent 运行时
> 文档日期：2026 年 8 月 18 日
> 状态：思路与设计阶段，尚未实现

## 一、项目背景与定位

DSH 是 DeepSeek 于 2026 年 8 月 13 日开源的 Agent 运行时框架，核心命题为 Agent = Model + Harness，采用"一切皆插件"（Everything is a plugin）架构——模型、工具、技能、会话、沙箱、存储、循环调度乃至 UI 全部是可替换的 Cordis 插件，连 agent loop 本身都可被替换。[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)[$TRAE_REF](https://venturebeat.com/technology/deepseek-harness-launches-as-open-source-rival-to-claude-code-alongside-v4-pro-on-api-with-higher-prices)

本方案要在 DSH 生态中实现三个协同插件，打通一条目前无人覆盖的闭环：**从会话中自动捕获错误 → 提炼为教训 → 晋升为可复用技能 → 在后续执行前主动注入预警，避免重犯**。同时提供项目/全局双层知识库，弥补现有记忆插件的作用域空白。

## 二、生态调研：已有插件与空白

### 2.1 技能管理方向

| 插件 | Star | 能力 | 缺什么 |
|---|---|---|---|
| DSH 原生 skills 子系统 | — | 6 个根目录优先级 100–600 扫描，兼容标准 SKILL.md 格式，`ctx.skills.register()` / `registerProvider()` 运行时注册 API，`disable-model-invocation` / `user-invocable` 调用策略控制 | 只管"发现与加载"，不管生命周期 |

### 2.4 调研结论：三个真实空白

| 空白 | 现状 | 机会 |
|---|---|---|
| **空白一**：从 Trajectory 自动捕获错误→提炼→晋升 Skill 的闭环 | MisakaNet 做了被动查询共享库，dsh-noema 做了通用记忆，但无人把"错误发生→Trajectory 抽取→LLM 提炼→置信晋升→挂 Preset"打通 | 做主动捕获的私有学习闭环 |
| **空白二**：原生项目/全局双层作用域的知识库 | DSH skills 有 6 级优先级但记忆插件几乎都是单层全局存储 | 把 skills 的作用域哲学移植到知识库 |
| **空白三**：执行前主动注入错误预警 | MisakaNet 是 agent 主动调 search 去查（模型得先想到去查），无人在工具执行前拦截注入预警 | 把错误记忆从被动检索变成主动防御 |

## 三、整体架构：三个插件协同的闭环

### 3.1 数据流与协同关系

```
Trajectory 事件流（append-only，DSH 原生）
   │
   ├─ tool/result(isError=true) ──→ dsh-errata（自动捕获+提炼）──→ 教训条目
   │   turn/end 后用户纠正                                                │
   │   同一工具连续失败 N 次                                              │
   │                                          置信度达标 ↓
   │                                                                    │
   │                                                       dsh-lesson-promote（错题本晋级：草稿+审批落盘）
   │                                                                    │
   └─ 任务上下文 ─→ dsh-knowledge（项目/全局双层）← 检索时合并
        ↑                                              │
        └──── 执行前预警注入 ←── 命中失败模式匹配 ←────┘
              （订阅 tool/start，工具执行前查本地错误库）
```

### 3.2 三个插件的分工

| 插件 | 角色 | 触发时机 | 输出形态 |
|---|---|---|---|
| `dsh-lesson-promote` | 错题本晋级：教训 → 技能草稿 → 审批落盘（含同名冲突守卫） | 教训计数达标（distilled）时扫描生成草稿，用户显式 approve | 技能草稿 + 正式 SKILL.md（技能生命周期归已装 `dsh-skills-manager`） |
| `dsh-errata` | 错误捕获→模式提炼→教训沉淀 | Trajectory 里出现 tool/error 事件时 | 错误教训条目（可转成 Skill） |
| `dsh-knowledge` | 知识库（全局/项目双层） | Agent 检索时、上下文注入时 | 知识条目 + 检索结果 |

三者通过 Cordis Context 共享一套条目 Schema，`errata` 产出的教训可以"晋升"为 `lesson-promote` 里的 Skill，也可作为 `knowledge` 的一条记录——形成"错误→教训→技能/知识"的闭环。

## 四、各插件详细设计

### 4.1 dsh-knowledge：双层作用域知识库

#### 作用域设计

直接对齐 DSH 原生 Preset 的 `agent → preset → global` 解析，做显式双层：

- **全局知识库（global）**：跨工作区的事实、规范、通用教训。存于 `~/.dsh/knowledge/global/`。
- **项目知识库（project）**：绑定当前工作区（workspace 根目录）。存于 `<workspace>/.dsh/knowledge/`，随项目走、可进 Git。
- 可选第三层 **会话级（session）**：临时记忆，仅当前会话，会话结束可"晋升"或"丢弃"。

检索时按 `session → project → global` 合并，越近优先级越高；冲突时项目层覆盖全局层。这样既满足"全局整体 + 项目记录"，又不用自造作用域机制——直接复用 DSH 已有的 fallback 优先级哲学，这是把 DSH skills 的作用域模型移植到知识库。

#### 存储模型

不走传统向量数据库 + RAG 重路线。社区记忆插件的经验是：**本地文件持久化 + 分层上下文注入 + LLM 自我整理**已经够用，且更可观测。[$TRAE_REF](http://m.toutiao.com/group/7674767880499626554/)

采用 Markdown 文件 + frontmatter 的条目格式（与 DSH 原生 Skill 格式一致，便于互转）：

```yaml
---
id: kb-2026-0818-001
scope: project            # project | global | session
workspace: /path/to/repo  # project 层必填
category: convention      # convention | fact | decision | pitfall
tags: [auth, jwt]
created: 2026-08-18
last_used: 2026-08-18
hit_count: 3
confidence: 0.8           # 来源置信度
source: trajectory-ref:evt_12345  # 可追溯到原始事件
---
正文：条目内容
```

检索用轻量 BM25 / 标签过滤 + LLM rerank，或直接文件路径分层 + 关键词索引。

#### 注入策略（分三档）

知识多了一塞就爆上下文。注入策略分三档：

- **主动注入（preset 加载时）**：只注入"该 Agent 角色必读"的少量全局条目（如该项目编码规范、禁忌操作）。通过 Preset 配置一个 `knowledge.injections` 列表。
- **被动注入（按任务检索）**：Agent 调用 `kb.search(query)` 工具，返回 Top-K 条目片段，由模型决定是否采用。这是主路径。
- **触发式注入（错误预警）**：当 `errata` 检测到当前工具调用与历史失败模式匹配，**在工具执行前**注入预警。这是"避免将来发生错误"的核心机制。

#### 与现有插件差异

| 维度 | dsh-noema | dsh-knowledge（本方案） |
|---|---|---|
| 作用域 | 全局 `~/.agent-memory/`，workspace 文件是"读进来" | 原生项目/全局双层，项目层随 Git 走 |
| 存储对齐 | 自有 Noema 格式 | 对齐 DSH Skill 格式，便于互转 |
| 设计取向 | 通用记忆 + 跨工具导入 | 项目知识库 + 团队共享 |

### 4.2 dsh-errata：自动捕获错误学习闭环

#### 数据来源：订阅 Trajectory 事件流

DSH 的 Trajectory 是 append-only 的完整事件流（turn/start、step/start、工具调用、参数、返回、错误），这是天然的数据源。`errata` 插件应**订阅事件**而非自己写捕获逻辑：[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)[$TRAE_REF](https://36kr.com/p/3938529497562503)

- 监听 `tool/result` 里 `isError=true` 或非零退出的 shell 事件；
- 监听 `turn/end` 后用户纠正（"不对，应该…"这类负反馈）；
- 监听 Agent 自身的 retry 模式（同一工具连续失败 N 次）。

每条错误记录建议结构：

```
{
  id, ts, workspace,
  task_intent,           // 任务意图
  tool,                  // 出错工具
  args_hash,             // 参数哈希前缀，用于匹配
  error_type, error_msg,
  root_cause_hint,       // 可选，LLM 提炼
  fix,                   // 修复方式
  related_skill_id,      // 关联的 Skill（晋升后填）
  trajectory_ref,        // 指向原事件，可回溯
  confidence,            // 置信度
  status                 // raw | distilled | promoted
}
```

`trajectory_ref` 指向原事件，方便回溯——这是 DSH Trajectory 回放能力的延伸，Claude Code 给不了的能力。[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)

#### 写入路径：Agent 自主写 + LLM 后台提炼双层

直接让 Agent 在出错当下写条目往往噪声大、表述差。分两层：

- **即时轻量记录**：出错时只记 `trajectory_ref + error_type + tool`，不写"教训"。
- **后台提炼**：定期（或会话结束、或条目达阈值）让 LLM 回看一批同类错误，压缩成"教训条目"（含触发条件、根因、修复模板），写入知识库或晋升为 Skill。这复用社区记忆插件"定期让 LLM 回头审视完整工作上下文"的思路，但把产物落地为结构化条目而非自由文本。[$TRAE_REF](https://36kr.com/p/3938529497562503)

注意 DSH 创造模式下动态生成的插件**仅存于内存、重启即消失**——所以存储层必须落盘（文件或 SQLite），不依赖 Cordis 内存 Context 做持久化。[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)

#### 与 MisakaNet 的互补关系

| 维度 | MisakaNet | dsh-errata（本方案） |
|---|---|---|
| 数据来源 | 人提交 issue，维护者审核 | 自动从本地 Trajectory 捕获 |
| 共享范围 | 跨 agent 共享库（公开） | 私有教训（本地） |
| 触发方式 | Agent 主动调 search 查询 | 被动订阅 + 主动注入预警 |
| 产物 | 共享 lesson（Markdown） | 私有教训条目，可晋升为 Skill，可推送为 MisakaNet 候选 |

两者不替代而是互补：私有教训达到高置信后，可推送到 MisakaNet 作为共享 lesson 候选，形成"私有学习→公共贡献"的溢出。

### 4.3 lesson-promote：错题本晋级（v3.0 由 dsh-skill-manager 更名）

#### 定位

只做"错题本晋级"，把 `errata` 沉淀的反复失败教训晋升为 DSH 技能；技能的**生命周期管理（安装/启用/停用/更新/移除）归已安装的 `dsh-skills-manager` 插件**（skill provider，name=`skill-manager`，rank 50），本插件不重复实现：

- **晋升管道**：从 `dsh-errata` 的可晋升条目自动生成 Skill 草稿（一个 `.md` + frontmatter），进入待审核队列。
- **审批落盘**：用户显式 `approve` 后把草稿落盘为 `<workspace>/.dsh/skills/<name>/SKILL.md`（内置 skill-filesystem 自动加载），落盘前做**同名冲突守卫**——平台已有同名技能（来自已装插件/runtime/user/bundled）时拒绝，已装插件优先。
- **无版本、无回滚**（v3.0 删除：技能版本管理归已装 `dsh-skills-manager`）。

#### 与 DSH 原生 skills API 的衔接

DSH 提供两个运行时注册 API：`ctx.skills.registerProvider()`（自定义 provider）与 `ctx.skills.register()`（单技能注册）。实现修订后（v2.1 起）**不再调用这两个注册 API**：

- 草稿只写 `.dsh/lesson-promote/drafts/`，`approve` 落盘 `.dsh/skills/<name>/SKILL.md` 即被内置 `skill-filesystem`（项目层 rank 100）自动发现加载；运行时注册 rank 250 反而会被同名遮蔽，且"同名预检查"会命中自己刚写的草稿导致自阻塞（均已实测）。
- v3.0 起本插件只**只读** `ctx.skills.snapshot({ cwd })` 做同名冲突守卫。

#### 晋升机制

错误教训积累到一定置信度（如同类错误出现 ≥3 次、且 LLM 提炼出稳定修复模板）应"晋升"为 Skill：

1. `errata` 标记条目 `status='distilled'`（同类错误计数达标）；
2. `lesson-promote` 定期扫描可晋升条目，生成 Skill 草稿（`.md` + frontmatter，写入 `.dsh/lesson-promote/drafts/`）；
3. 草稿进入"待审核"队列，由用户或 Agent 显式调用 `lesson-promote approve <name>` 确认（同名冲突守卫通过后）落盘为正式 Skill；
4. 正式 Skill 写入 `<workspace>/.dsh/skills/<name>/SKILL.md`，由内置 skill-filesystem 按项目层 rank 100 自动加载。

Skill 本身按 DSH 既有 Skill 机制加载（`/skill` 命令、Preset 配置），`lesson-promote` 只管"错题本晋级"（扫描、草稿、审批、冲突守卫），不重造 Skill 执行路径，也不做技能生命周期管理。

## 五、关键技术要点

### 5.1 Cordis 副作用回收与持久化的边界

这是现有所有记忆/知识插件都未明确处理的工程空白。Cordis 的卖点是组件卸载时自动回收副作用。但写入知识库文件、注册工具、注入上下文，都应通过 Cordis Context 声明为副作用，这样：[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)

- 用户在创造模式里试验一个知识写入插件，觉得不好→卸载，Cordis 自动回滚它写入的文件改动，不留垃圾；
- 同一会话里 Agent 自己装了个临时 Skill 插件，任务结束自动回收，不污染下次会话。

但**持久化知识不能被回收掉**——所以需区分两类副作用：

| 副作用类型 | 是否参与回收 | 示例 |
|---|---|---|
| 临时注入（可回收） | 是 | 上下文注入的临时片段、运行时注册的临时 Skill |
| 正式落盘条目（持久） | 否，标记为持久 | 写入 `.dsh/knowledge/` 的知识条目、晋升的正式 Skill |

这个边界必须设计清楚，否则会出现"插件卸载后知识消失"的怪 bug。做好它是一个明确的差异点。

### 5.2 触发式预警：执行前主动注入

这是"避免将来发生错误"的核心，也是现有生态最大的空白。实现路径：

1. 订阅 Trajectory 的 `tool/start` 事件（工具即将执行）；
2. 查本地错误库，匹配条件为 `tool + args_hash 前缀`；
3. 命中则在该次工具调用的上下文里注入预警："上次类似调用（tool X, args Y）失败，原因是 Z，建议先 W"；
4. 模型看到预警后自主决定是否调整。

这与 MisakaNet 的本质区别：MisakaNet 是 agent 主动调 `search` 去查（模型得先"想到要去查"）；本方案是**在工具执行前拦截并注入**，把错误记忆从被动检索变成主动防御。

### 5.3 安全与质量闸

错误教训会被注入上下文影响后续决策，质量差会污染 Agent。建议：

- **写入需审批**：错误→教训的提炼由 LLM 生成草稿，晋升为 Skill 或写入全局库需用户/高级 Agent 确认（DSH 有审批策略机制，直接复用）。
- **项目知识进 Git**：`.dsh/knowledge/` 可入版本控制，团队共享 + 可 review + 可回滚。
- **全局知识只读保护**：全局库写入走单独审批通道，避免单个项目污染全局。
- **过期与遗忘**：给条目加 `last_used` 和 `hit_count`，长期不命中的条目降权或归档——对应自进化研究里"是否遗忘旧能力"的评估缺口，Cordis 不解决，插件要自己加。

### 5.4 与自进化研究版图的对应

Cordis 解决的是"装/卸"的工程能力，但"这条教训对不对、会不会过拟合近期反馈、会不会误伤其他任务"——这些智能层评估 Cordis 不碰，清华 SEAGym 那条线在研究。[$TRAE_REF](https://damodev.csdn.net/6a7e927f662f9a54cb9c95a2.html)

本方案在质量评估上只能靠审批 + 命中统计 + 过期归档这套工程手段兜底，短期内没法做到全自动可信。这是这类插件的天花板，设计时要承认它。

## 六、落地路径

### 6.1 分阶段实施

| 阶段 | 内容 | 验证目标 |
|---|---|---|
| 第一步 | `dsh-knowledge` 项目层 + 主动注入 + `kb.search` 工具 | 最小可用，验证注入链路 |
| 第二步 | 接 Trajectory 订阅做 `dsh-errata` 即时记录 + 触发式预警（不做提炼） | 验证"避免重复错误"价值 |
| 第三步 | 加后台提炼 + 晋升机制 + 全局层 + `dsh-skill-manager` | 形成闭环 |
| 第四步 | 副作用边界细化 + 与 MisakaNet 互通（高置信教训推送为候选） | 生态协同 |

每一步都用创造模式 + Trajectory 回放自测，确保副作用回收干净、条目可追溯。

### 6.2 打包为 DSH 插件

按 DSH 插件规范打包：[$TRAE_REF](https://www.bibigpt.co/blog/posts/deepseek-harness-agent-skills-compatible)

- `package.json` 声明 `dsh.bundle.patch` 指向 `cordis.patch.yml`；
- `cordis.patch.yml` 贡献一条带 `id` 和 `name` 的 `insert` 行；
- 插件 `apply()` 里通过 `ctx.skills.register()` 在运行时注册，**不占有任何配置行**，避免与其他插件覆盖冲突；
- 用户用 `dsh plugin --profile <name> add <target>` 安装，target 可以是 npm 包名、本地路径、或 git 仓库（含子目录）。

## 七、差异化总结

| 维度 | 现有最强 | 本方案差异 |
|---|---|---|
| 知识库作用域 | dsh-noema（单层全局） | 原生项目/全局双层，对齐 DSH skills 优先级哲学 |
| 错误学习 | MisakaNet（被动查询共享库） | 自动从 Trajectory 捕获 + 主动注入预警 |
| 技能管理 | dsh-skill-viewer（基础 CRUD） | 加晋升管道、版本、回滚 |
| 副作用边界 | 无人明确处理 | 区分临时可回收 vs 持久化，不互相污染 |
| 闭环 | 三者各占一角，无人打通 | "捕获→提炼→晋升→预警"完整链路 |

单一空白有人占了一角，但**"自动捕获→提炼→晋升→主动防御"这条闭环是空的**。这是本方案的机会。与现有插件的关系不是替代，是补链：知识层可基于 dsh-noema 的存储模型加双层作用域；错误层与 MisakaNet 互补（私有自动捕获 + 共享查询库）；技能层在 dsh-skill-viewer 之上加生命周期。

## 八、实现修订说明（2026-08-21，对应 v2.1 需求文档）

本文档为设计思路（v1）。实际实现（`DSH插件-需求与技术设计.md` v2.1）在 DSH 0.1.0-rc.8 平台实测后，对以下机制做了修订：

1. **技能生效机制：文件落盘优先，弃用 `ctx.skills.register()`**。实测发现内置 `skill-filesystem` 默认扫描 `<project>/.dsh/skills`（项目层 rank 100），写文件即生效——若草稿阶段就写入 `.dsh/skills/`，草稿会未经审批提前生效；而 `ctx.skills.register()` 的 runtime 层 rank 250 低于 FS 副本，同名时永远被遮蔽；"同名预检查"还会命中自己刚写的草稿导致 approve 永久自阻塞。修订后：草稿只写 `.dsh/lesson-promote/drafts/`，`approve` 才落盘 `.dsh/skills/<name>/SKILL.md`，平台自动加载。
2. **版本快照目录**：v2.1 从 `~/.dsh/skill-manager/versions` 迁至 `~/.dsh/dsh-plugins/skill-manager/versions`（前者已被 `dsh-skills-manager` 占用）；**v3.0 起删除版本快照与回滚**（技能版本管理归已装 `dsh-skills-manager`）。
3. **安装链路**：`dsh plugin add` 的 link 安装无法解析 `workspace:*` 依赖，必须先仓库根 `pnpm install` 建立 shared 工作区链接；宿主依赖改用 npm 版本（`dsh-*@0.1.0-rc.8`），仓库可独立构建测试。
4. **§5.2 副作用边界**：原"运行时注册的临时 Skill（可回收）"条目已删除——不再有运行时注册。
5. **预留项明确**：LLM 提炼、turn/end 提炼触发、`session` 层知识库、`archived` 过期归档、`promoted` 状态均为预留，未在 v2.1 实现。
6. **v3.0 更名与解冲突**：插件更名 **skill-manager → lesson-promote**（包 `@dsh-plugins/lesson-promote`，插件 id / 工具名 / 服务 `ctx.lessonPromote` 同步更名），删除版本/回滚，approve 增加同名冲突守卫（已装 `dsh-skills-manager` 的 provider 名 `skill-manager` 与技能命名空间均不再与本插件冲突）。

设计思路（§三–§七）中"捕获→提炼→晋升→预警"闭环、双层知识库、三档注入、安全质量闸等核心定位不变。
